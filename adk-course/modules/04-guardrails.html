Guardrails: Why the AI Can't Break Anything

Five layers of plain-code safety between an AI suggestion and a real change

The bank vault rule: never one key

Bank vaults use dual control: no single person can open them. This agent applies the same idea to AI. The model may suggest isolating a computer, but five independent checks stand between that suggestion and anything happening.

1
Read-only tools

No AI agent is ever given a tool that can change anything. A test scans the code to prove it.

2
Checks before every tool call

Callbacks enforce a call budget and lock each run to its own scenario's data.

3
Policy code reviews every proposal

Fixed rules block dangerous actions, whatever the AI says.

4
A named human approves

"agent" or "system" can't approve. A rejection needs a reason.

5
The write server re-checks, plus a kill switch

Even the Executor is refused without a matching approval.

Layer 2: a checkpoint before every tool call

A callback is like an airport security gate that every passenger walks through. ADK calls it before each tool use, and it can wave the call through or stop it.

CODE · soc_agents/common/callbacks.py 
    def before_tool(tool, args: dict[str, Any], tool_context) -> dict | None:
        if tool.name == FINAL_ANSWER_TOOL:
            return None
        key = f"temp:tool_calls:{tool_context.invocation_id}:{tool_context.agent_name}"
        used = tool_context.state.get(key, 0)
        if used >= max_calls:
            return {"error": (f"Tool budget of {max_calls} calls is used up. Do not call any more investigation "
                              f"tools. Submit your final answer now by calling {FINAL_ANSWER_TOOL} with the "
                              "evidence you already have, and list what you could not check under gaps.")}
        tool_context.state[key] = used + 1
        return None
PLAIN ENGLISH

Runs before any tool call: it sees the tool, its inputs and the session.

If the agent is submitting its final answer…

…always let it through (otherwise it could never finish).

Make a counter label unique to this run and this agent.

How many tool calls has this agent made so far? (0 if none.)

If it has hit its limit…

…refuse, and tell it: no more searching…

…submit your final answer now…

…with what you have, and list what you couldn't check.

Otherwise add one to the counter…

…and let the call go ahead ("None" means "no objection").

🐛
A real bug this project hit

The first version also blocked the final-answer tool. When an agent ran out of budget it couldn't submit its report, wrote plain text instead, and the whole run crashed. The two lines at the top fix it. Lesson: a guardrail must always leave a safe way to finish.

Layer 3: the policy rulebook

After the Planner proposes actions, ordinary code checks each one against fixed rules. The model can't argue its way past an if statement.

If this kind of action needs proof but the AI cited no event IDs…

…block it: "no evidence cited".

If the target is a whole group such as "all-staff"…

…block it: the blast radius is too large.

If it would isolate or kill something on a Tier 0 machine like DC01…

…block it: only the Incident Response team decides that.

⛔ blockedSaved for the audit record and can never be approved
🤖 auto_approvedLow impact only: AV scan, contact user, escalate, close case
⏳ pendingEverything else waits for a named human

Layer 5: the write server double-checks

Only the Executor, which is plain code, can start the write servers. Even then, each server re-checks the approval itself. Picture a bank teller who phones the manager to confirm a large withdrawal even though you're holding a signed slip.

💡
Defence in depth

Each layer assumes the one before it might fail. That's the habit to ask an AI coding tool for in any risky system: "don't trust the caller, re-check permissions where the action actually happens".
