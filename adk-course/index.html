01

One Alert, Start to Finish

What this agent does for a bank's security team, and the journey of a single alarm through it

The job: a security team that never sleeps

Banks have a SOC. Every day it gets hundreds of alarms called alerts. Most are harmless. A few are real attacks, and a human analyst needs about an hour to dig into each one.

This project is a team of AI helpers that does that first hour of digging in a few minutes. It never touches a real system unless a human says yes.

🚨
Input: one alert

e.g. "Office application spawned encoded PowerShell on WS-042"

🔎
Work: AI agents investigate

They read logs, computer activity, account data and threat intelligence

📋
Output: verdict, plan and ticket

"Real attack, high severity. Here's what to block. Please approve."

🧪
It's a lab, not a real bank

Everything is fake: "Contoso Bank", its users and its attacks. The security tools are pretend versions that read from files, so you can experiment safely.

Think of a hospital emergency room

The word "triage" literally comes from the ER. When a patient arrives, a nurse decides how urgent it is, specialists run tests in parallel, a doctor makes the diagnosis, the patient signs consent, and only then is treatment given.

The very first line of code that runs

When you open the chat, the first thing that runs is not AI. It's a small piece of normal code called Intake. It reads your message and decides what to do with it.

CODE · soc_agents/intake.py 
if m := ALERT_RE.search(text):
    alert_id = m.group(0).upper()
    handled = state.get("handled_alerts") or {}
    if alert_id in handled and not re.search(r"\b(rerun|re-run|again)\b", text, re.I):
        return _reply(f"`{alert_id}` was already investigated in this session (incident `{handled[alert_id]}`).\n\n"
                      f"{_queue_table(handled[alert_id])}\n\nSay `rerun {alert_id}` to investigate it again.")
    scenario = alert_id.split("-")[1]
    if not _scenario_exists(scenario):
        return _reply(f"Unknown alert `{alert_id}`: no scenario `{scenario}` in the lab data.")
    state["current_alert"] = alert_id
    state["scenario"] = scenario  # every tool call of this run is scoped to it
    return None  # run the AI pipeline
PLAIN ENGLISH

Look for something shaped like an alert ID (e.g. ALR-A2-001) in your message.

If found, keep the ID, in capital letters.

Get the list of alerts this chat has already investigated.

If this alert is on that list and you didn't say "rerun"…

…reply "already investigated" and show its approval queue…

…instead of paying for a second full AI run.

Cut the ID at the dashes: the middle part, "A2", is the scenario.

If no such scenario exists in the lab data…

…say "unknown alert" and stop.

Write the alert ID on the shared notepad (the "state") for later agents.

Also note the scenario, so every agent reads only that scenario's data.

Returning "nothing" means "carry on and start the AI agents".

💡
Not everything should be AI

Reading an ID from text is a job for a simple rule. It's instant, free and never wrong. Good AI systems keep AI for judgment calls and use plain code for everything predictable. When you ask an AI to build something, say so explicitly: "do this in plain code, not with the model".

02

What Is an ADK Agent?

Google ADK explained from zero: the five things every agent is made of

ADK in one sentence

Google ADK is a toolkit that turns an LLM into an agent: an AI that can look things up and work toward a goal, not just chat.

Think of hiring a new employee. A smart graduate (the model) is useless on day one without an onboarding kit. ADK is that kit.

🧠

model

Which brain they use: Gemini, or Qwen on your own vLLM server.

📜

instruction

The job description: "You are the Triage agent. Decide severity…"

🔑

tools

The keycards: which systems they may look at (SIEM, AD…).

🗂️

output_schema

The form they must fill in: fixed boxes such as severity and users.

📥

output_key

The out-tray: where they drop the filled form for the next person.

A recipe that builds the Triage agent.

Its name tag is "triage".

A one-line summary of its job.

Use the strongest model tier ("pro").

Its job description, which never changes between runs.

The systems it may look at:

the SIEM: only these 3 lookups,

the EDR: only fetching events,

Active Directory: only user and PC lookups,

the case system: only case details and change records.

(end of the tool list)

Don't re-read the whole chat history: cheaper and faster.

The answer must fit the TriageResult form.

Save the answer on the shared notepad under the label "triage".

Before every tool use, run the safety checks (max 8 tool calls).

Before every model call, tidy the prompt (more in Module 5).

(done)

💡
An agent is mostly configuration

Notice there's no "how to investigate" logic in this code. The thinking happens inside the model. Your code only sets what it knows, what it may touch, and what shape its answer takes. That's why you change agent behaviour by editing prompt.py, not by writing new code.

Swapping the brain: Gemini or your own server

The agents never name a specific model. They ask for a tier ("pro" for hard thinking, "flash" for quick work), and one small function decides which model that means, using settings in the .env file.

def get_model(tier: str) -> str | BaseLlm:
    """Model for a tier: 'pro' (reasoning), 'flash' (specialists), 'lite' (guard/judge)."""
    provider = os.environ.get("SOC_MODEL_PROVIDER", "vllm").lower()
    if provider == "vllm":
        model = os.environ.get(f"VLLM_MODEL_{tier.upper()}") or os.environ.get("VLLM_MODEL")
PLAIN ENGLISH

"Give me the model for this tier."

(A note explaining the three tiers.)

If it's the local vLLM server…

…use the tier-specific model if one is set, otherwise the general VLLM_MODEL.

SOC_MODEL_PROVIDER=geminiUse Google's Gemini with an API key: easy, but the free tier is limited

How Agents Share Work

Session state passes results between agents, and MCP tools let them read the security systems

Passing the baton: session state

Agents never talk to each other directly. They work like a relay race: each runner finishes their lap and hands a baton to the next. In ADK the baton is the session state.

Each agent's output_key says which label it writes. Here's what's on the notepad after one A2 run:

scenario"A2", written by Intake from the alert ID
triageSeverity, users, hosts, time window, questions for specialists
edr_findings · siem_findings · …One report per specialist, each citing event IDs
investigationVerdict, timeline, MITRE ATT&CK, compromised vs clean
response_planProposed actions, each marked allowed/blocked by policy
incident_report · incident_idThe ticket, and the ID used by the approval queue

How an agent reads the baton

A word in curly braces inside an agent's instructions is a placeholder. Just before the model reads its instructions, ADK swaps {triage} for Triage's actual answer.

💡
Structured outputs make teamwork reliable

Because every agent must fill in a fixed form (its output_schema), the next agent always gets the same fields in the same place. When you design multi-agent systems, ask for "structured output with a schema" rather than free text.

Tools: one standard plug for every system

Agents reach the SIEM, EDR, AD, threat intel and case systems through MCP. Think of USB-C: one plug shape, any device. Each security system is a small MCP server exposing a few "lookups".

CODE · mcp_servers/siem_mcp.py 
    @read_tool(mcp)
    def get_alert(alert_id: str) -> dict:
        """Get one SIEM alert by id (e.g. ALR-A2-001), including entities, MITRE techniques and evidence event ids."""
        for a in store.alerts:
            if a["alert_id"].lower() == alert_id.lower():
                return a
        return {"error": f"alert {alert_id} not found"}
PLAIN ENGLISH

Register this as a read-only tool agents may call.

The tool is called get_alert and takes one input: an alert ID.

This description is what the model reads to decide when to use the tool, so it matters.

Go through every alert in the (fake) SIEM data…

…and if the ID matches (ignoring upper/lower case)…

…return that alert.

Otherwise say clearly that it wasn't found, never make one up.

Each agent only gets the plugs it needs. In mcp_tools("siem_mcp", ["get_alert", "get_events"]), the list is a tool filter. Triage can't search the SIEM in bulk, and no agent at all has a tool that changes anything.

04

Guardrails: Why the AI Can't Break Anything

Five layers of plain-code safety between an AI suggestion and a real change

The bank vault rule: never one key

Bank vaults use dual control: no single person can open them. This agent applies the same idea to AI. The model may suggest isolating a computer, but five independent checks stand between that suggestion and anything happening.

1
Read-only tools

No AI agent is ever given a tool that can change anything. A test scans the code to prove it.

2
Checks before every tool call

Callbacks enforce a call budget and lock each run to its own scenario's data.

3
Policy code reviews every proposal

Fixed rules block dangerous actions, whatever the AI says.

4
A named human approves

"agent" or "system" can't approve. A rejection needs a reason.

5
The write server re-checks, plus a kill switch

Even the Executor is refused without a matching approval.

Layer 2: a checkpoint before every tool call

A callback is like an airport security gate that every passenger walks through. ADK calls it before each tool use, and it can wave the call through or stop it.

CODE · soc_agents/common/callbacks.py 
    def before_tool(tool, args: dict[str, Any], tool_context) -> dict | None:
        if tool.name == FINAL_ANSWER_TOOL:
            return None
        key = f"temp:tool_calls:{tool_context.invocation_id}:{tool_context.agent_name}"
        used = tool_context.state.get(key, 0)
        if used >= max_calls:
            return {"error": (f"Tool budget of {max_calls} calls is used up. Do not call any more investigation "
                              f"tools. Submit your final answer now by calling {FINAL_ANSWER_TOOL} with the "
                              "evidence you already have, and list what you could not check under gaps.")}
        tool_context.state[key] = used + 1
        return None
PLAIN ENGLISH

Runs before any tool call: it sees the tool, its inputs and the session.

If the agent is submitting its final answer…

…always let it through (otherwise it could never finish).

Make a counter label unique to this run and this agent.

How many tool calls has this agent made so far? (0 if none.)

If it has hit its limit…

…refuse, and tell it: no more searching…

…submit your final answer now…

…with what you have, and list what you couldn't check.

Otherwise add one to the counter…

…and let the call go ahead ("None" means "no objection").

🐛
A real bug this project hit

The first version also blocked the final-answer tool. When an agent ran out of budget it couldn't submit its report, wrote plain text instead, and the whole run crashed. The two lines at the top fix it. Lesson: a guardrail must always leave a safe way to finish.

05

Speed, Cost and Debugging

Where the time and money go, the tricks that cut them, and how to find out what went wrong

Where the time goes: model calls

Every time an agent thinks or uses a tool, the model reads its whole prompt again. The amount of text it reads is measured in tokens. In one real A2 run, the SIEM and EDR specialists each read about 50,000 input tokens, mostly their own growing tool results.

🧹

No chat history

include_contents="none": each agent sees only its inputs, not everyone's earlier tool results.

🗜️

Compact tool results

No pretty-printing and no empty fields: about 40% fewer characters. At most 10 events per search.

✂️

Word limits

Schemas say "max 2 sentences", "max 4 findings". Shorter answers are faster answers.

⚙️

Plain-code Reporter

The ticket is a template, so one whole model call (the biggest output) is gone. 7,974 → 2,653 characters.

💤

Thinking off

Qwen normally "thinks" in hidden text before answering. VLLM_THINKING=off skips that.

The barista who already knows your order

A good barista starts your usual drink when you walk in. Model servers do the same with a prompt cache. If a prompt starts with exactly the same text as last time, that part is skipped. ADK always adds "Your internal name is…" to each agent's system prompt, though, so the start was different at every hand-off between agents.

CODE · soc_agents/common/callbacks.py 
def shared_system_prompt(callback_context, llm_request) -> None:
    """before_model_callback: move the agent-specific system text into the first user message."""
    config = llm_request.config
    own = config.system_instruction if config else None
    if isinstance(own, str) and own.strip() and own != SHARED_SYSTEM_PROMPT:
        from google.genai import types
        role = types.Content(role="user", parts=[types.Part(text="ROLE INSTRUCTIONS:\n" + own)])
        llm_request.contents = [role, *llm_request.contents]
        config.system_instruction = SHARED_SYSTEM_PROMPT
    return None
PLAIN ENGLISH

Runs just before every model call, holding the finished request.

(What it does: move each agent's own rules out of the system prompt.)

Look at the request's settings…

…and grab this agent's own system prompt.

If it's real text and not already the shared one…

(load the message building blocks)

…turn this agent's rules into a message labelled ROLE INSTRUCTIONS…

…and put that message first in the conversation.

Then give every agent the same shared system prompt, so the cache can match it.

"None" means "carry on with the call".

Gemini free tier vs your own server

Free Gemini is like a toll road with a daily pass: about 5 cars per minute and 20 per day for each model. One incident needs about 50 model calls, so it runs out fast. Your vLLM server has no pass to buy, but it's one road, so traffic jams happen.

⏱️
Gemini: 429 errors

The code waits and retries (up to 8 times). The daily limit can only be fixed by billing or switching to vLLM.

🚦
vLLM: at most 2 requests at once

Four specialists firing together caused a connect timeout. Now they queue for 2 slots and retry with growing pauses.

🔒
vLLM: data stays local

On the free Gemini tier Google may use your data, so only synthetic data belongs there.

When things break: read the flight recorder

Planes carry a black box that records everything. ADK's web UI has one too: the Events tab (every model call and tool call, in order) and the State tab (each agent's saved answer). Here are real bugs from this project and how they showed up.

1
Symptom: the run stops right after Triage

Events showed httpx.ConnectTimeout → four specialists overloaded vLLM → fix: concurrency limit and retries.

2
Symptom: "Validation Error … Input should be a valid list"

Qwen sent a list as text → the schema now accepts list-as-text instead of failing.

3
Symptom: typing "Approve" re-ran the whole investigation

Every message was treated as a new alert → plain-code Intake now handles commands.

4
Symptom: the policy blocked killing the malware

The target was written as "svchost-update.exe on WS-042" → the policy now finds the host inside the text.

💡
Give the AI the evidence, not your guess

When an agent run fails, copy the exact error and the last few Events into your request to the AI coding tool. "It stopped after triage" leads to guessing. "httpx.ConnectTimeout while 4 specialists ran in parallel" leads to the real fix in one step.
